## Recommendation and three realistic representations

**Recommend B1: canonical extended-range, sRGB-encoded RGB stored as float32 NPY.** Standard sRGB primaries/white point and an explicitly specified extended transfer interpretation are retained, while negative/above-one values are represented rather than clamped. This is **not** ordinary bounded sRGB, nor a claim that a monitor can show those colours. Profile-relative preservation is a qualification goal, not a new verified result.

## Proposed B1 end-to-end contract

1. **Interpret once locally:** validate source SHA, RGB/orientation and supported ICC, then transform tiled RGB into extended encoded sRGB in float64. No `[0,1]` clipping, eight-bit conversion, per-image min/max scaling, automatic colour correction or guessed profile. Reject ambiguous/unsupported/non-finite inputs. Round only the declared storage representation to float32.
2. **Prepare model views:** aspect-preserving float resampling to224 with recorded inverse geometry; letterbox with existing ImageNet RGB mean. Store one224×224×3 float32 array per selected image. Resampling can overshoot; preserve and report finite extended values rather than silently clipping them. Exact float resampling/interpolation and its new expected outputs must be fixed before implementation; old uint8 tensor-equivalence assertions cannot be claimed unchanged.
3. **Load safely:** validate manifest/file size/hash, NPY header allowlist, exact dtype/shape/order, finite values and qualified range envelope; use `allow_pickle=False`, bounded headers and read-only loading. No arbitrary objects, extra files, traversal or links. Transpose to CHW; normalize `(RGB−mean)/std` using existing `[.485,.456,.406]` / `[.229,.224,.225]`. Do not divide these already scaled floats by255 again.
4. **Reuse architectures, not the old input contract:** existing `preprocess_rgb`, `RGBDataset` and display renderer assume PIL/uint8; introduce a separately versioned exploratory B adapter instead of feeding them floats or weakening their checks. Retain model factories, five-logit order, frozen-backbone/BatchNorm controls and trainer mechanics after integration tests. Extended inputs are mathematically consumable by PyTorch, **not proven equivalent to ImageNet pretraining**. No claim of unchanged accuracy; no new architecture comparison until both use the same approved B preprocessing.
5. **Explain/display consistently:** retain full-resolution canonical arrays for eligible Validation00733/00734/00766; model inputs come from the same colour/geometry path. Reuse class-specific Grad-CAM mathematics and inverse geometry. A separate display adapter produces a fixed, documented sRGB preview and overlay. Label the first pane **“unoverlaid display preview; gamut conversion may lose colour”**, not byte-identical original. Keep canonical/source provenance separate. Display-only clipping/mapping must be explicit and approved; never use that preview for fitting or imply a narrow-gamut display preserves every canonical colour. Proposal explanation wording requires review; calibrated clinical display fidelity is unproven.

- Full-size CAM payload is `12 × sum(W×H)` bytes. **If** all three were35,431,818 pixels, they would add≈1.188GiB, giving≈1.599GiB combined raw payload. This is a planning example, **not measured CAM dimensions or bundle size**. - On the16GiB Mac, process one source at a time with bounded tiles; no whole-cohort decode. A35.4MP float32 RGB buffer alone is≈405.5MiB; avoid full float64/Lab copies, use qualified tiled/memory-mapped output and release each source. Benchmark actual peak RSS before claiming16GiB suitability or a completion time.
- Colab batch16 float32 inputs alone are≈9.19MiB; activations, models, workers and checkpoints dominate additional RAM/VRAM. Start with the bounded head-only configuration and few workers after approval. Provision a GPU session/host memory with headroom and measure usage; hardware/time availability is not guaranteed. No need to load full-size CAM arrays during training.
