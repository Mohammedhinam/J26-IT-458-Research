The function accepts generated bytes only, without a filesystem loader, dataset selection, CLI or production dispatch. It copies original JPEG coding tables and complete SOS/entropy/EOI bytes unchanged. It removes EXIF (including DateTime/GPS/MakerNote), supported metadata-only XMP and comments; embedded JFIF thumbnails are removed while display-density fields remain unchanged. It never calls JPEG save/re-encoding. This preserves existing decoded JPEG pixels, not the pixels before the original lossy JPEG encoding.

## Qualified subset and remaining limitations

Only single-scan baseline three-component RGB8 JPEGs are accepted, within explicit byte/geometry bounds. Unknown APP metadata, HDR/gain maps, extended/unknown XMP, progressive/multiscan JPEG, malformed ICC and nonidentity orientation stop. Rendering-related XMP must not be silently deleted. This intentionally narrow policy may reject legitimate files; no real-source compatibility is claimed.

ICC preservation can also preserve identifying text. Therefore the caller must supply a separately reviewed non-identifying ICC hash allowlist. Tests allow only independently generated profiles. **No real profile hash has been approved.** Hash allowlisting is a prerequisite, not proof that a profile is anonymous. Source metadata inside EXIF is removed as a container; source pixels and meaningful display interpretation must still be evaluated within the supported contract. Visible identifying information in pixels is outside metadata sanitisation.

This standalone study does not implement the real cohort, nine protected Test-alias exclusion, content-group gates or upload authorization. Existing selection and research gates remain mandatory and unchanged. No dental images, real ICC payloads, raw caption/TXT content or protected Test data were accessed. No external upload package, download, training or inference occurred.

## Three lines to understand

- `output = SOI + kept_headers + original_scan`: removes metadata without recompressing image content.
- `np.array_equal(original_rgb, cleaned_rgb)`: independently decodes both generated files and rejects any pixel change.
- `profile_before == profile_after` plus trusted profile SHA: preserves colour interpretation while requiring separate ICC privacy review.

Viva: Why preserve ICC? Because the same RGB numbers can describe different colours under different profiles; blindly removing ICC may change displayed colour.

Technical references: [ICC profile embedding](https://www.color.org/profile_embedding/), [Pillow JPEG/ICC documentation](https://pillow.readthedocs.io/en/stable/handbook/image-file-formats.html#jpeg). The implementation is a narrow generated-only study, not a universal JPEG/privacy standard.
